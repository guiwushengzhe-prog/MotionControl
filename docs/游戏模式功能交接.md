一个游戏可以有几套按键（比如和平精英的「步行」「开车」），控制中用任意现有触发切换。

## 用户已经确认的需求

1. 一套「模式」只包含按键映射：每个触发圈、身体动作、姿势、本游戏口令分别按什么键（包括「不绑」）。圈的位置、头控/握拳视角、识别参数各模式共用，切换时不变。
2. 切换方式先做两种：「切到指定模式」和「切到下一个模式」（轮着切；只有两个模式时就是来回切）。「按住时临时切换」以后再说。
3. 每次重启、每次换游戏都从默认模式开始，不记住上次的模式。
4. 不加专门的「切回去」口令，用户自己在通用口令或任何触发上绑「切换模式」。
5. 名字叫「模式」，不叫「方案」：程序里「游戏方案」已经指一个游戏整包分享的配置（`game_bundle`）。

## 已完成（未提交前的进度，现已作为进行中提交保存）

### 共用规则 `motioncontrol_shared/profile_schema.py`
- 新输出类型 `mode`：`target` 为 `NEXT`、`DEFAULT` 或模式编号 `mode-xxxxxxxx`（8 位小写十六进制）；永远是点按；和宏一样不检查模式是否还在，失效时运行时什么都不做。
- `action_catalog()` 增加 `mode`（`library: "modes"`，`targets: [DEFAULT, NEXT]`）。
- 新常量和函数：`DEFAULT_MODE_NAME="默认"`、`MAX_GAME_MODES=8`（默认之外）、`MODE_NAME_MAX=12`、`normalize_mode_name`、`is_mode_id`、`normalize_modes`（编号、名字不重复，「默认」保留，覆盖用 `normalize_overrides` 规范化）。

### 云端规范化 `motioncontrol_shared/canonical.py`
- 整份配置（`profile_selection`）可带可选的 `modes_by_profile: {游戏编号: [{id, name, overrides}]}`；空列表丢掉，不带时输出与以前逐字节相同（哈希不变）。
- 单游戏分享包（`game_bundle`）可带可选的 `modes`。
- **没有升 schema 版本**：只加可选字段，旧程序和旧云端会忽略模式、只用默认那套；升版本反而会让旧版本拒绝整个文件。（之前计划里说过「升一级」，后来按这个理由改了，需要告诉用户。）云端要重新部署才认模式；没部署前上传会静默丢掉模式。

### 电脑端存储 `motioncontrol/game_profiles.py`
- 默认模式就是原来的 `overrides_by_profile[游戏]`，其他模式存在选择文件的 `modes_by_profile[游戏]`（列表顺序就是「下一个」的轮换顺序）。旧文件不需要迁移。
- `_load_selection` 校验 `modes_by_profile` 结构。
- 新方法：`effective_profile(mode_id=None)`（返回值多了 `mode: {id, name}` 和 `modes` 列表，默认模式编号为 None）、`modes()`、`mode_bindings()`（各模式生效绑定，语音建语法用）、`add_mode(name, copy_from=None)`（复制默认或某个模式）、`rename_mode`、`remove_mode`、`set_modes(game_id, modes, check=None)`（装分享配置用）。
- `set_overrides(..., mode_id=None)`：存默认或某个模式；模式已删掉时抛 `ProfileSelectionChanged`（接口回 409）。
- 删除自建游戏时连同它的模式一起删。

### 内核 `motioncontrol/control_kernel.py`
- `configure_bindings(bindings, *, mode=None)`：原来的整套重装，多了当前模式标签；公共部分抽成 `_install_bindings_locked`。
- 新 `switch_bindings(bindings, *, mode=None)`：控制中换模式。
  - 新旧模式里键没变的触发照常继续（边踏步边切，W 不断；点按的不会因为切换再按一次）。
  - 键变了、此刻还按着的触发进 `_mode_held`：旧键立刻松开，要放开再做才算新的一次（防止举双手切到「开车」后，新模式里举双手绑的键被立刻按下）。
  - 变了的触发清掉条件输出已选的键和循环计数；切完立刻按新绑定分发一次。
- 分发 `_dispatch_controls_locked`：`active` 减去 `_mode_held`；`mode` 类型在触发开始那一帧调 `_mode_action_handler(target, trigger)`（`configure_mode_action_handler` 装上）。
- 状态里新增 `game_mode: {id, name}`。
- 已用临时脚本验证：举双手只触发一次切换；W 不断；右手圈 E→F 时旧键立刻松开、离开再进圈才按 F。**还没写成正式测试。**

### 语音 `motioncontrol/voice_backend.py`
- 重建识别器会重新加载 Vosk 中文模型（约 42MB），期间听不了口令，所以切模式时不能重建。
- `configure_profile_bindings(bindings, mode_bindings=None)`：`mode_bindings` 是本游戏所有模式的绑定，本游戏口令按模式先后从所有模式取，一起进识别语法，顺序与当前模式无关。
- 新 `switch_profile_bindings(bindings)`：只重建「说法 → 口令」对照表；语法合集没变就不重建识别器。
- 不在当前模式里的口令说了也不对应任何动作。本游戏口令真正执行时按内核当前绑定查键（`server._execute_voice_action` 读 `KERNEL.control_bindings`），所以内核一换，口令输出自动跟着换。

### 服务端 `server.py`
- 运行时状态 `GAME_MODE = {"game", "id"}`，不写文件；`_active_mode_id()`、`_active_profile()`。换游戏或模式被删时自动回到默认。
- `_apply_effective_profile()` 按当前模式装绑定，语音带上所有模式的绑定。
- `switch_game_mode(target)`：算出目标模式 → `KERNEL.switch_bindings` + `VOICE.switch_profile_bindings` → 推给手机。不写文件。
- 触发路径：
  - 区域/动作/姿势：内核 → `_run_bound_mode_action` → `SYSTEM_COMMANDS` 后台队列 → `_execute_voice_action` 里带 `trigger` 的 `mode` 分支 → `switch_game_mode`。
  - 本游戏口令绑了 `mode`、通用口令选了 `mode`：`_queue_mode_switch` 交给同一个后台队列。**原因**：普通口令是语音服务持着 `VOICE._lock` 执行的，而切换要按「`PROFILE_UPDATE_LOCK` → `PROFILES._lock` → `VOICE._lock` → `KERNEL._lock`」的顺序拿锁，当场切会和保存配置死锁。
- 接口：
  - `GET /api/game-profiles/selected?mode=<id>`：读某个模式给映射表编辑；不带就是当前模式。返回多了 `active_mode`。
  - `POST /api/game-profiles/overrides` 支持 `mode_id`；返回多了 `active_mode`。
  - `POST /api/game-profiles/modes`：`{op: "add", name, copy_from?}`、`{op: "rename", id, name}`、`{op: "remove", id}`，可带 `profile_id` 防止游戏已切换（409）。
  - `POST /api/game-profiles/mode`：`{target: "NEXT"|"DEFAULT"|编号}`，开始页手动切换用。
- 给手机的配置包按当前模式生成，多了 `game_mode` 字段（旧手机忽略）；口令清单 `voice_command_catalog` 按当前模式。
- 装分享配置：整份配置带了某游戏的模式就整组换上，旧格式不动本机原有模式；单游戏分享包带 `modes` 就换上。
- 配置事务失败回滚时，恢复当前模式、内核绑定、语音口令和模式合集。

## 重启运行中的后台（需要用户在管理员确认里点「是」）

1. `GET http://127.0.0.1:8766/api/shutdown`，等 8766 端口不再监听。
