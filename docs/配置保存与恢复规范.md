# 配置保存与恢复规范

配置的定位、保存、反馈和恢复采用共用入口。新增功能按本规范接入，已有专用实现按审查记录逐步迁入；不能因为一个模块有保护，就宣称全部配置都已覆盖。

## 文件与文档

- 用户配置位置只从 `motioncontrol.user_paths` 获取。通用文件名登记在 `motioncontrol_shared.user_layout.USER_DATA_FILES`，不在组件里重新拼接用户目录，也不引用开发机器的固定路径。
- 每份文档有明确格式和校验函数。读取、编辑、导入与恢复复用同一份校验；未知格式保留原件并说明原因，不静默写成默认值。
- 配置写入与后台重试共用配置锁；需要同时切换识别状态时按“配置锁、内核锁”的固定顺序执行，读取回执同样遵守，不能边重试边提交同一文档。
- `SettingsPersistence` 管理有效副本、待保存状态、错误翻译和重试。`config_transaction` 管理原子替换及多文件恢复记录；禁止新建一套“临时文件写入再替换并忽略异常”的保存代码。
- 恢复记录按文件区分，避免头部、通用设置、动作和宏共用同名记录。多文件操作显式把主文档及有效副本纳入同一个事务。

## 两种提交方式

实时偏好与校准可以先应用：例如头部和通用设置，写盘暂时失败不能打断正在进行的识别。失败时保留最新快照，页面显示“已应用、尚未保存”，限次重试；重试只保存快照，不重新执行动作或追加记录。超过上限后等待用户重试，不能在每一帧反复写盘。

动作库、宏、游戏绑定等采用严格提交：先构造独立草稿并校验全部字段，文件事务成功后才切换内存状态。失败必须保留原有列表、触发进度、文件与副本；不能返回“失败”却在内存中留下一个新动作或新宏。触发规则和进度在成功提交后一起更新。

校验出错也属于失败。例如同时修改名称与阈值，阈值不合法时名称不能部分生效。调用方传入的原对象不得成为未提交修改的载体。

## 共用状态与页面反馈

- 通用设置、头部设置及其他已接入文档登记到内核的配置状态入口。新增文档使用 `register_settings_document`，提供当前完整文档，用同一入口执行重试和明确修复。
- `settings_persistence` 表示整体配置状态；`settings_write` 只描述本次操作实际涉及的文档。一个无关动作库损坏，不能把已经成功新建的宏报告为失败。
- 保存回执列出相关文档身份及版本。页面只在同一后台确认这些版本已落盘后完成原草稿；旧响应不能覆盖新状态，新后台不能替旧后台声称草稿已保存。
- 自动补存完成后更新状态，不再重复提交原操作。后台重启保留旧草稿，用户选择重试后才重新提交。
- 错误提示先说明哪份配置、当前是否生效、是否保存及可执行的下一步。复用中性提示与共享按钮，不新增独立配色，也不靠按钮文字推断操作类型。

## 损坏与恢复

优先恢复经过校验的最近有效副本。无有效副本时保留原件并阻止默认值静默覆盖；明确选择修复后先归档原文，再保存当前文档。仅剩损坏副本时同样保留原文。相同损坏内容使用固定摘要归档，避免重复生成副本。

应用启动时先恢复事务，再创建读配置的对象。正常退出有待保存状态时说明情况并保留程序；关闭过程不能把待保存状态伪装成成功。

完整本地备份恢复继续按成熟软件设计审查实施：先预览，备份当前状态，再执行可回退替换。用户目录身份、账户与配对凭证、跨电脑的机位校准单独处理；不能把运行中复制几个文件当成完整恢复。

## 必须核对的行为

修改保存路径或增加配置时，针对实际影响核对：写入失败不部分提交、有效副本可恢复、损坏原文保留、自动重试有上限、旧回执不覆盖新状态。涉及多个文档时，至少覆盖后一个文件失败后的回退；涉及触发规则时，确认失败不改变原进度。检查使用隔离目录和合成输入，避免修改用户正在使用的配置或设备。
